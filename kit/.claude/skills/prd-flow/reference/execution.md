# Execution (C5 step 6, and C2, C3, C6 with code)

Read by the agents that execute and by the maintainer. The chief (the prd-flow main thread) never reads this page: its card in `SKILL.md` carries the loop and the failure routing table, the single home of who owns each failure. The chief dispatches and routes by return fields; executors write, test and commit; the reviewer is the only reader of diffs; executor `close` closes. Commands come from `repo.md`.

## Where to execute
| ID | Rule |
|---|---|
| E01 | Checkpoint (the single home of these numbers): past about 120k tokens in the chief, or with more than 2 waves left, the chief updates `## Chief` of `state.md` (phase, `Next:`) and continues in a fresh session with `/prd-flow resume <slug>`. The fresh session reads only `state.md`: `## Chief` gives the phase, `review: N/5`, pending items and `Next:`; `## Plan` (written by docs) gives the plan path, the wave table and the `Execution:` line: per wave dispatch the executors, review always, recheck after a fix; then executor `close` |
| E02 | After the plan is approved, the chief may offer execution in a fresh session on the fast model. The chief never reads the plan: `## Plan` of `state.md` alone gives the task IDs and models per wave; each executor reads its own card by range |

## Wave loop
| ID | Step |
|---|---|
| E03 | Baseline: the chief runs `scripts/gates.sh baseline <slug>` in the background in the target repo, after the plan commit (C5) or the surveyor card (C2, C3, C6) (`dispatch.md` DP06), never inside another agent. C4 close does not require one. Executors start without waiting for it. Without a baseline `scripts/gates.sh close` fails with "baseline missing" (C2, C3, C5, C6); a baseline taken at close would hide the change's own failures |
| E04 | Waves (the single home of the width): the docs agent writes the wave table (the `WAVE n:` lines of `gate.py --step plan`, each task with its model) into `## Plan`, the chief's only source. At most 4 executors per wave, dispatched by the chief in one message in the background (`dispatch.md` DP02); no polling, the returns arrive by themselves; the chief does not wait on one agent while other independent work exists. Each prompt is the dispatch line of `SKILL.md` with `Mode: task` and the task line `Task: <ID>` (in C2, C3, C6: the card path the surveyor returned); the executor reads its card, `Decisions:` and `Leave:` lines included. The model is the one the table marks. A failed task reruns alone. On rate limits the wave shrinks to 2. A big file has a serial chain |
| E22 | Isolation only when needed: a worktree per executor only when parallel tasks of a wave share build or test state that interferes; otherwise one tree with disjoint Owns |
| E05 | Commits belong to the agents: each executor commits its own Owns with the message of its card and the `Rules:` or `Case: none (...)` trailer, checks that nothing it wrote is left out, and returns `Commit: <hash>`. The chief runs no git command and reads no diff. A stray or uncommitted path is the executor's to fix; the reviewer reports one it sees. A gap that is a rule or contract divergence returns `Route: surveyor short` (R09, E08 to E10); a missing technical detail returns `Route: user` with the question and options, resolved before the task that depends on it |
| E06 | A plan with a parallel wave (2 or more tasks) gets one review per wave by the `prd-flow-reviewer` on the combined wave diff; a serial plan (every wave has one task) gets one review after the last wave on all the wave commits (`## Plan` carries the `Review:` line); a serial plan accepts that a Critical in an early wave is found only after later waves built on it, a known trade-off. Whatever the cards say. The chief's task line carries the wave and the commit hashes from the executors' returns; the reviewer reads the wave's cards for rules, `Decisions:`, `Leave:` and `Lens:` itself. `Lens:` adds a specialized rubric from `repo.md` "Reviewers"; `Lens: none` means no extra lens, never no review. Findings route by its return (`review.md`) |
| E07 | Resume: an agent that already holds the context, is under about 150k tokens and did not hit its ceiling (V08) is continued with SendMessage; otherwise a new agent of the same role with the handoff from the last return. A correction folded into a plan is an in-place docs `trd-plan` `adjust`, not a revert and a redo. When the user interrupted an agent, the replacement first saves what it left (`git --no-pager diff`) as a patch in `state/<slug>/`. The chief's dispatch ledger (`dispatch.md` DP04) keeps a duplicate dispatch from starting |

## Rule change in the middle of execution (short C5, R09)
| ID | Step |
|---|---|
| E08 | An agent that meets behavior no approved rule covers (review.md V06) stops its own task and returns `Route: surveyor short: <the behavior, the task>`. Tasks already running finish; the surveyor's return says which of their work stands and which is redone. The `prd-flow-surveyor` in short mode runs K01, K02, K11, K12 on the touched rules only, writes a confrontation of at most 15 lines in product language (R07) and the prepared questions, and appends the reopened dimensions and the dated rows to `rules.md` and `delta.md`; it never touches `## Chief` nor resets the review counter. Outside a C5 (the task line says `Case short C5 outside a C5`) it creates `rules.md` (first line `Scope: short C5 outside a C5`) and `delta.md`, and renders `interview.md`, `approved-rules.md` and `changes/NNN-<slug>/decisions.md`. More than one rule, or a dimension the change never covered: its return routes to a full C5 |
| E09 | The chief shows the confrontation, asks the prepared questions and passes the answers verbatim to docs `rules` with the date; docs fills the dated rows of `rules.md` with their `Confirmed:` line, adds `DEC-` rows, replaces the rows in place, re-renders (a re-approved ID replaces its earlier row; old text literal for the CHANGELOG) and runs `gate.py --rules` until green |
| E10 | Approved: docs `short <YYYY-MM-DD>` applies the PRD (`--applied` green), then the TRD, appends the new tasks to the plan (outside a C5 it creates `plan.md`), rewrites the stopped cards and refreshes the wave table in `## Plan`. Execution resumes from the returned table. No hand edits of PRD or CHANGELOG; the HTML is never touched (`prd-writing.md` "HTML"). The review counter does not reset without explicit approval |

## Cost per agent
The weight of an agent is the context it resends on every call, times the number of calls. An executor with 300k tokens and 150 calls costs more than the rest of the route; the chief's context is the most expensive of all, which is why it executes nothing.

| ID | Rule |
|---|---|
| E12 | No agent opens a subagent. Parallelism belongs only to the chief, by wave |
| E13 | Executor and fixer run on `sonnet`. `opus` only when the plan marks the task as a new safety decision (or another reason written on the task line) |
| E14 | An agent that hit its ceiling (review.md V08), or passed about 150k tokens, returns a handoff of at most 10 lines (files touched, red tests, next step) in its Route; the chief dispatches a new agent of the same role with it. At most 2 reruns per step inside an agent; the third failure returns `blocked` with the error lines and a Route |
| E15 | The agent prompt names the task, never the plan; the agent reads only its card |
| E16 | Tests run with output redirected to a file, and only the `FAILED` and `ERROR` lines and the summary come back into context |
| E17 | Brake: an agent that hits its ceiling twice, or a wave that takes more than twice the time of the previous one, stops the execution; the chief reports to the user what is left and the cost so far. Never run for hours without reporting |
| E18 | **Verification per batch, not per agent.** An executor runs only its own new test (see it fail, implement, see it pass) plus `fix-files` and `lint-files` on its files; no related tests, suites or gates. When a wave ends the chief starts ONE background `scripts/gates.sh verify <slug>` (related tests of every file changed in the wave, structure tests, docs gates, output to a file) with the wave reviewer; failures and findings go to one `fix` dispatch and the next verification reruns only what failed. **Compare:** the chief starts `scripts/gates.sh compare <slug>` in the background during the last review (the full suite, once, against the baseline); close never runs the suite inline, it reuses that result |
| E19 | **Moving code is done by script, in C6 refactors only.** The agent decides the map (which symbol goes to which module) and `scripts/gates.sh move <source> <start> <end> <destination> [--at LINE]` cuts and pastes the block by line range; the model only fixes imports and calls. Never retype a function body. Elsewhere Edit. With huge test files, split code and tests first and prove statically (import check, type check, lint); run tests in parts afterwards |
| E23 | **Reap at every wave end:** the chief runs `scripts/gates.sh reap` when a wave's returns are in; it certifies that no process is left (`left: 0`), agents do not |
| E11 | No cost line is written by hand: the run telemetry records every agent, and `gates.sh retro` (inside close) prints the findings |

## Closing
| ID | Rule |
|---|---|
| E20 | After the last wave and its review, the chief dispatches executor `close`. In a C5 it runs `promote.py <slug>` first (`--hold <ID> --reason <words>` for a row blocked by an eval, a deploy or another repository; drops markers, fills Source from the deliveries, writes the CHANGELOG, archives the change folder; it never touches the HTML); C2, C3, C4 and C6 have no promote. It commits its output (the tree is clean in `docs` and `changes` before the gate), writes the promote result in `## Close` (before the gate: a passing close deletes the folder, so nothing is written into the state folder after close starts), then runs `scripts/gates.sh close <slug>` reading its stdout (never redirected into the state folder; nothing under `.claude/prd-flow/` is ever committed). **Close order (G2):** lint, trailers, docs, then the compare result of E18 (never the suite inline), then `gate.py --final` and retro. It returns the retro findings (severity, value, threshold, evidence). Every error it cannot fix leaves with a Route per the failure table of `SKILL.md`: missing `Source:` to executor `fix`, a fold to docs `fold`, any other failing step to executor `fix` with the printed lines, each followed by executor `close` again. A passing close deletes the state folder of the slug, so promote always runs before close, never after. The chief never reads `promote.py`, `retro.md` or a PRD row. Findings become tasks only when the user asks |
| E21 | Deliveries are per task: `.claude/prd-flow/state/<slug>/deliveries/<task>.md`, written by its executor (no shared file for parallel writers), at most 16 lines: what was created, the symbols later tasks consume, the `Source:` lines. Each reads `Source: <ID>: <path::symbol>`, one line per approved code rule the task's Owns implement (rewritten rules included), never a list or range of IDs on one line; `promote.py` reads exactly these to fill the PRD Source column. A `Source:` line is required only for rules whose Change via is `code`; rules changed via config, env, prompt, data or a handoff stay `planned`, are listed in promote's output and are closed by their own route (`repo.md` "Change routing"). A consumer reads the producer's delivery, never its code |
