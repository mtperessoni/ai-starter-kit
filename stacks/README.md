# Stack recipes

The kit is stack-free; `/ai-kit install` adapts it to each project with these recipes. A recipe is data, not code: how to detect the ecosystem, which commands fill `ai-kit.json`, how the stack's linter enforces the structure rules that text cannot see (AR03 function and class size, AR04 inheritance, AR05 shared state, AR09 import direction), and what CI needs.

The installer reads only the recipes whose detection signals match, and **verifies every command by running it** before writing it. A recipe is a starting point; the project's own scripts and configuration win (an existing `make test`, `npm run test:unit`, `just lint` is used as is).

| Recipe | Detect |
|---|---|
| [python.md](python.md) | `pyproject.toml`, `setup.cfg`, `requirements*.txt`, `uv.lock`, `poetry.lock` |
| [node.md](node.md) | `package.json` (JavaScript or TypeScript, any framework) |
| [go.md](go.md) | `go.mod` |
| [jvm.md](jvm.md) | `build.gradle(.kts)`, `pom.xml` (Java, Kotlin) |
| [dotnet.md](dotnet.md) | `*.csproj`, `*.sln` |
| [rust.md](rust.md) | `Cargo.toml` |
| [ruby.md](ruby.md) | `Gemfile` |
| [php.md](php.md) | `composer.json` |
| [generic.md](generic.md) | Nothing above matches, or an ecosystem not listed |

In a monorepo, the root `commands` call the workspace runner (`pnpm -r`, `turbo run`, `nx run-many`, `go test ./...`, `make`, or one command per package joined with `&&`), so `scripts/gates.sh` stays the single entry point; `source_dirs` lists every package source folder.

## Recipe format
Every recipe has the same sections, so the installer reads them the same way:

1. **Detect**: files and what they reveal (package manager, framework, test runner).
2. **Commands**: the values for `ai-kit.json` `commands` and `tests`.
3. **Structure enforcement**: linter rules for AR03, AR04, AR05, AR09 with the kit's limits, and how to baseline existing violations so CI is green on day one. Also AR24 complexity, AR25 dead code, AR26 duplicates, AR27 typing (or "not applicable") and AR22 runtime dispatch (the linter rule if any, else "review"), each with a shrink-only baseline.
4. **Offline guard**: how the unit tier is kept off the network and the database.
5. **CI setup**: the step that replaces the placeholder in `ci.yml`.
6. **Ignore**: generated paths for `ai-kit.json` `ignore` and `.gitleaks.toml`.
7. **Layout**: common examples of the ecosystem and its frameworks, not a closed list (the installer describes whatever it finds), and how each is declared in `ai-kit.json` as `layout`, `areas` and `map_dirs` (AR01, AR20). A framework unit of cohesion (Django app, NestJS or Angular module, Rails pack, Spring feature package, Go package, Rust crate) is an area.
8. **Test naming**: `tests.mirror_patterns`, `tests.match_symbol`, where tests live (AR10; suffix test names such as `*Test` or `*IT` need a matching entry in `test_patterns`), and the `tests.junit_xml` flag that makes the runner write a JUnit report (TS37).
9. **Generated files**: `generated_patterns` and the marker line the generator writes (AR28). The ratchet accepts by default any match in the first 5 lines of the case-insensitive regex `auto-?generated|generated by|code generated|automatically generated|@generated|do not edit|don't edit|do not modify`; a generator whose header matches none sets the `ai-kit.json` key `generated_marker` (a regex).
10. **Framework exemptions**: `unique_name_exempt` (names the framework imposes, AR02), base classes or mixins it requires (AR04), its state primitives (AR05), and `id_header_lines` when files open with package and imports (AR06).
11. **Snapshots**: the runner's update flag agents must not use, and the snapshot globs (TS39).
12. **Contracts**: the schema or API snapshot the framework already produces, or the dump command (DS30), as `contracts` entries.
13. **Setup**: `commands.setup`, the one command that makes a fresh clone or worktree ready to test (IN12).

Where a tool, rule name or flag is not certain, the recipe says "look up" and the installer searches before writing it.
