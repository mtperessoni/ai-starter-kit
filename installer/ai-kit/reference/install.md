# install

## Steps
| Step | Does | Leaves |
|---|---|---|
| I1 | K01 and K02. `Glob` the project root and two levels down for manifests and configuration: package manifests, lockfiles, test configs, linter configs, CI files, `Makefile`/`justfile`/`Taskfile.yml`, `CLAUDE.md`, `AGENTS.md`, `.specify/`, `docs/`, `.claude/`, `specs/`, `Dockerfile*`, compose files. Detect whether tests use Docker (a compose file started by tests, `testcontainers` or equivalent in dependencies). Detect monorepo workspaces and whether spec-kit is in use (`.specify/` with templates or scripts, `/speckit-*` commands in `.claude/`) | file list |
| I2 | Read `<kit>/stacks/README.md` and only the matching recipes. Read the project's own scripts (package scripts, Makefile targets, CI steps): they win over the recipe | stack profile |
| I3 | Source layout (IN11): describe how code is really organized, whatever it is (by product area, by technical role, by framework convention, mixed, or anything else), in one free-text line for `layout`; find the entry point and the test folders. Propose `areas` (area name to globs of its files, for code outside `feature_root`), `map_dirs` (folders that carry a `CLAUDE.md` map) and, from what the repository shows (hotspots, crowded folders, generic names, missing maps, big tests, noise), the readiness improvements that would help most. Also detect generated and vendored paths for `generated_patterns` and `ignore`. Large trees: one Explore agent with these questions, answers only | layout, areas |
| I4 | Run each candidate command once with output to a file (`.claude/prd-flow/state/_install/`), read the summary: test runner on one existing test file, lint verify, type check, import check, the whole unit tier once (its failures become the first baseline). Also verify `commands.setup` (IN12: one command that makes a fresh clone or worktree ready to test) and record the time of one related run for `tests.related_budget_seconds`. Write down the failure line format to derive `tests.failure_regex` | verified commands |
| I5 | Questions, one round of at most 4 (K07): the project's one-line description; the domain principles of the constitution (offer 2 or 3 drawn from the README, the code and the existing docs, recommended first); the variants and tenants (platforms, channels, customers) if any; the reviewers wanted (risk classes: security, data contracts, safety, compliance); where a new area goes (recommended: a new feature folder); for a non-feature layout, "keep the layout with the readiness plan (recommended) or plan the move to feature folders". Base branch and CI platform are detected, asked only when ambiguous | answers |
| I6 | Plan table (K03): every file with create, merge, replace or skip; commands for `ai-kit.json`; linter rules to add; the branch name. Wait for yes | approval |
| I7 | Copy the payload from `<kit>/kit/` following `ownership.md`. Kit-owned files are copied byte for byte, including the five agents `kit/.claude/agents/prd-flow-{surveyor,docs,executor,reviewer,recheck}.md` to `.claude/agents/` (a project agent with the same name is shown as a diff, never overwritten silently), `promote.py` and `close_gate.py`. Never copy `gitignore.kit` as a file: append its lines to `.gitignore` (including `.ai-kit/runs/`). When `scripts/gates.sh` already exists: rename it to `scripts/gates.project.sh`, then list in `ai-kit.json` `commands.project_targets` every target of it that must keep the project's behavior (the kit's `gates.sh` delegates those, and the targets it lacks, to the renamed file); confirm with `scripts/gates.sh <target>` for one of each. Merge the kit's `.claude/settings.json` (hooks and permissions) into the project's as `ownership.md` says, keeping the project's own | files |
| I8 | Fill the project-owned files (table below). No `<...>` or `{{...}}` placeholder may remain outside `docs/templates/` | filled files |
| I9 | Structure enforcement from the recipe: add the recipe's structure enforcement (linter rules or a structural test) for AR03, AR04, AR05, AR09, AR22, AR24 to AR27, each with a shrink-only baseline of today's violations. When the project already has its own structural test, skip the overlapping checks instead of keeping two allowlists: list them in `ai-kit.json` `ratchet.skip` (check names as `--init` prints them: `long_modules`, `long_tests`, `banned_names` (alias `generic_names`), `duplicate_names`, `no_prd_id`, `no_feature_map`, `long_feature_maps`, `crowded_dirs`, `generated_without_marker`). Run `python scripts/ratchet.py --init` and put its output into `ai-kit.json` `allowlist` (`limits.skill_md_bytes` stays at its default 6144). Update `docs/code-structure.md` "Checked by" when a rule ends as "review". When I1 found Docker: the container rules TS27 to TS36 as the recipe's "Containers" section says (labels on every compose service, volume, network and build, `purpose` from the environment, a session sweep in the integration tier, guards before builds, teardown failures that fail) | enforcement |
| I10 | Reviewers: for each risk class chosen in I5, copy `docs/templates/reviewer-agent.md` to `.claude/agents/<risk>-reviewer.md` and fill it: the principle it guards, 4 to 7 checks specific to this code (read the relevant folders by symbol), severities, 3 examples. Register them in `repo.md` "Reviewers" | agents |
| I11 | Verify (below). Fix what fails; what cannot be fixed becomes a line in the report | results |
| I12 | Write `.ai-kit/manifest.json` (`ownership.md`). Commit `chore: install ai-starter-kit <version>` (one commit; the PRD and TRD come later in their own commits) | commit |
| I13 | Report and next steps (below) | report |

| `ai-kit.json` telemetry | The `telemetry` section with the kit's defaults (TM08), no tuning at install |

| `.gitleaks.toml` | The recipe's ignore paths |

## Verify
All must pass, or be reported:
- `scripts/gates.sh lint`
- `scripts/gates.sh ratchet` (green right after `--init`)
- `scripts/gates.sh imports`
- `scripts/gates.sh settings-check` (no deny rule on a file the flow writes); `commands.fix_file` and `commands.lint_file` set from the recipe, each run once with `{files}` on one real file (K05)
- `scripts/gates.sh setup`, `scripts/gates.sh hotspots` and, when `contracts` is configured, `scripts/gates.sh contracts`
- `python scripts/related_tests.py <one existing source file>` prints its mirror test and importers; `scripts/gates.sh related <that file>` runs them and prints only failures and the summary
- `tests.failure_regex` (IN17): take one real failure line of the stack (run one deliberately failing test in a temporary file, or use the line the recipe documents) and check that the regex captures the test id (`python -c` with `re.search`, the regex read from `ai-kit.json`); a regex whose backslashes were lost (for example `^FAILs+(S+)` for `^FAIL\s+(\S+)`) is fixed from the recipe before the baseline is recorded
- `scripts/gates.sh baseline install` records the baseline; `scripts/gates.sh compare install` reports zero new failures; `tests.baseline_deselect` lists a test that hangs or fails offline, with the reason in the report; `tests.always` lists the structure tests that join every related run; `tests.junit_xml` is set to the recipe's default for the stack
- Search and proxies (IN18): `rg` is on PATH (`command -v rg`; when missing, report it and name the install command of the platform, the tools fall back to slower search); when a token-saving proxy such as `rtk` rewrites commands, test runners and linters run as `rtk proxy <cmd>` (or the runner's own binary), because the proxy swallows their output and the gates parse it
- `python .claude/skills/prd-flow/scripts/gate.py` only reports that `docs/prd/INDEX.md` does not exist yet (expected until prd-create)
- When the `docker` section exists: `scripts/gates.sh guard` passes or names what to remove, and `scripts/gates.sh sweep` runs; `docker image ls --filter label=<namespace>.repo=<repo>` lists the images the repository built after one `scripts/gates.sh build`
- Telemetry: pipe one sample PreToolUse payload (`{"hook_event_name":"PreToolUse","session_id":"s1","tool_name":"Bash","tool_input":{"command":"echo ok"}}`) into `python scripts/telemetry_hook.py`; it prints nothing, exits 0 and one line appears in `.ai-kit/runs/default/events.jsonl` (delete that run folder after); `scripts/gates.sh retro` runs without error. Then run the hook commands registered in `.claude/settings.json` from another directory with `CLAUDE_PROJECT_DIR` set to the project: they exit 0 (the launcher resolves the script from that variable)
- A search for U+2014 over the files written (the Grep tool with the pattern `\x{2014}`) finds no em dash

## Report
In at most 20 lines: stack detected, files created and merged, commands verified, linter rules and baseline sizes, reviewers created, what failed, the commit. Then the next steps:
1. Add the global block once per machine if `install.sh` did not: `<kit>/global/CLAUDE.md` into `~/.claude/CLAUDE.md`.
2. `/prd-create` to write the PRD from the code (or by interview in a new project).
3. `/trd-create` to map the code and add the `CLAUDE.md` maps; in any layout it proposes the readiness plan (N4) and offers the optional move to feature folders (N5).
4. From then on, every change goes through `/prd-flow`.
