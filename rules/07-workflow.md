# Workflow (WF)

Every change to product behavior follows **PRD, then TRD, then plan, then code**. Starting from the code reproduces the defect and loses the decision. The `prd-flow` skill runs this workflow; these are its rules in catalog form.

## Gate and cases

| ID | Rule | Why | Lands in |
|---|---|---|---|
| WF01 | Every change and every question about product behavior starts with `/prd-flow`. Skip only for small changes (typo, log line, rename, one-line fix that changes no rule), test fixes, CI, dependency bumps and formatting | One entry point loads the right context every time | CLAUDE.md "Product rules flow" |
| WF02 | Classify each request into one case, one line; a request with several items gets one case per item | Each case has a different cost and route | skill SKILL.md "Cases" |
| WF03 | Cases: **C0 no PRD** (`docs/prd/INDEX.md` does not exist: hand over to `/prd-create` and `/trd-create`; WF36), **C1 query**, **C2 implement** an approved rule the code does not meet, **C3 bug** (code diverges, PRD confirmed right), **C4 stale PRD** (code right, PRD wrong, confirmed), **C5 rule change** (changed, new, gap, or defect the PRD documents as current behavior), **C6 refactor** (structure changes, behavior does not) | Named cases make routing deterministic | classification.md |
| WF04 | "Diagnose", "understand why", "plan" are C1 until the user asks for a change: show cause and options and wait | Diagnosis requested is only diagnosis | classification.md; R01 |
| WF05 | Fixing a defect that the PRD documents as current behavior is a rule change (C5), not a bug | The PRD said it does that; changing it is a decision | classification.md |
| WF06 | A request with no matching rule is a gap: C5, and the new rule enters the PRD before the code | Behavior without a written rule is an undocumented decision | classification.md |
| WF07 | A refactor that turns out to need a changed limit, text or order escalates from C6 to C5 | It stopped being structure only | classification.md |
| WF08 | Nothing is written in `docs/`, `src/` or `tests/` before its time: C5 from step 5 on; C2, C3, C4 and C6 after the user confirms the case | The user sees the current rule before anything moves | R01 |
| WF09 | Code and PRD answer facts; the user answers intent | Never ask what the code already says; never infer what the user wants | R02 |

## Rule change (C5)

| ID | Rule | Why | Lands in |
|---|---|---|---|
| WF10 | Before any interview, show the confrontation: current rule (literal), proposal, what changes for each actor, impact (related rules, variants, tenants, tests, specs, open questions), trade-offs and risks. Then ask: "This is the change I want", "Do not touch this rule" (back to C2 or C3), "Adjust the request" | The user decides with the impact on the table | impact.md; SKILL.md step 3 |
| WF11 | The impact sweep always covers the consumer contract in sibling repositories, safety nets removed or weakened, and the prerequisites to verify the rule (real model, database, backend) | Discovered late, each becomes an extra round with the user | impact.md K08 to K10 |
| WF12 | Removing or weakening a safety net (a guard, a list, a fallback, a switch, a wait) is a trade-off in the confrontation and a question in the interview, never an extra task during execution | Protections vanish quietly otherwise | impact.md K09; RV06 |
| WF13 | Protected rules (constitution principles, invariants backed by structural tests, registered exceptions) change only through an ADR or a constitution amendment, after explicit confirmation; ask whether the protection still holds, since the doc may be stale | Deliberate change of protections | impact.md "Protected rules" |
| WF14 | Replaced by WF42: the interview asks only the dimensions the pre-interview left `open` or `assumed` | Rounds are the most expensive part of the route | interview.md |
| WF15 | Questions: at most 4 per round in one AskUserQuestion; product language with a conversation or usage example and the effect on the user; a concrete scenario; options with the trade-off in the description, recommended first and marked "(Recommended)"; no rule IDs, symbol names or internal jargon in the question (IDs only in the read-back) | Users answer scenarios, not identifiers | interview.md; R07 |
| WF16 | Replaced by WF43: the interview exit is checked by `gate.py --rules` (Q3) on `interview.md` | A rule with an open dimension does not enter the PRD | interview.md |
| WF17 | The approver is `git config user.name`, recorded in `state.md` and the CHANGELOG entry | Traceability of who decided | SKILL.md step 1 |
| WF18 | Replaced by WF44 and WF45: the person confirms the rule diff at step 6 | Cheap, exact review of what changed | SKILL.md step 6 |
| WF19 | The plan is approved by the user as a table (ID, result, owns, depends on, model, reviewer) before any execution | Execution is the expensive part | agent-plan.md "Presentation" |
| WF20 | Replaced by WF46: a mid-execution rule change is the short C5 of R09 | No hand edits of the PRD during execution | SKILL.md R09; execution.md E08 to E10 |

## Commits, resumption, reporting

| ID | Rule | Why | Lands in |
|---|---|---|---|
| WF21 | Commit order: `docs(prd): ...` (PRD and HTML together), `docs(trd): ...`, `docs(changes): ...` (the plan), then one code commit per task. Conventional Commits, English, IDs in the message. No push and no PR without an explicit request | Docs land before code; history reads as the workflow | R03; WS |
| WF22 | When the branch is behind the base: `git diff --stat HEAD..origin/<base> -- <paths read>`; pull only if it touches the scope | Avoid needless merges mid-task | SKILL.md light route step 4 |
| WF23 | Resumption: `/prd-flow resume <slug>` reads only `state.md` and the current phase file; the pack is still valid when `git diff --quiet <base> origin/<base> -- <pack paths>` holds | Resuming costs one small file, not a replay | SKILL.md "State" |
| WF24 | Explaining what the system did in a real session: ask for its id and read the recorded evidence before concluding; without it, list the code paths that could explain it and which evidence would separate them | No confident guesses about production behavior | classification.md |
| WF25 | Final report: case, IDs touched, commits, plan path, out-of-scope divergences, and the retro findings of the run (or that it stayed within every threshold, TM) | The user sees outcome, debt and process problems in one place | SKILL.md "Final" |
| WF26 | Where the plan lives: `changes/NNN-<slug>/plan.md` with the next free number (S: only when the change has tasks), or only a publish or deploy task when the change is config or env. Workflow state stays in `.claude/prd-flow/state/<slug>/` | The plan sits in one folder with the intent of its change; the legacy spec amendment path no longer exists | agent-plan.md; AGENTS.md "Directory map" |

## Change folders and living truth

| ID | Rule | Why | Lands in |
|---|---|---|---|
| WF27 | Size is decided at classification and stated in the case line. **S**: C1, C2, C3, C4, C6, no folder or only `plan.md`. **M**: C5 with an evident design (no new data model, contract, external dependency or open technical unknown): `brief.md` and `plan.md`. **L**: C5 with a new data model, contract, external integration, technical unknown or feature area: `brief.md`, `design.md` and `plan.md` | The paperwork matches the risk | classification.md; AGENTS.md "Workflow"; constitution Development Workflow 2 |
| WF28 | The plan header carries `## Constitution check`: one row per principle the change touches (principle, how the plan honors it, or the justified violation). A violation is justified there, not in a separate table | One place to see which principles the change touches | agent-plan.md; constitution Governance |
| WF29 | The mandatory final task "Promote" moves what is durable to its living home (PRD, TRD, ADR, real schema or contract) and archives the folder with `git mv changes/NNN-<slug> changes/archive/NNN-<slug>` | A change folder holds intent, plan and state, never truth; archived, it cannot pass for current behavior | agent-plan.md; AGENTS.md "Workflow" |
| WF30 | Order of authority: constitution, then PRD (behavior), then TRD (structure), then code. An active plan governs only the order of work. Nothing under `changes/archive/` or a legacy `specs/` is read to learn current behavior | An old plan must not read as authority | AGENTS.md; CLAUDE.md |
| WF31 | `gate.py --trace`: every PRD rule whose Source is not `planned` is cited by a test file; untested rules are reported against the shrink-only `allowlist.untested_rules` (new untested rule: error; listed: warning; listed but now tested: error asking to remove it); the file named in Source exists | A rule without a proof is a claim | gate.py; ai-kit.json |
| WF32 | `gate.py --change <dir>`: every ID in `brief.md` exists in the PRD; every ID of a P1 slice is in the Contract of a task of `plan.md`; `brief.md` holds no rule row; `design.md` without size L is a warning | Behavior is written once, in the PRD; the brief only cites it | gate.py |
| WF33 | `gate.py --final`: no PRD row with Source `planned` or the pending marker, no `## Planned` section in `docs/trd/`, no folder in `changes/` outside `archive/`; CI runs it on pushes to the base branch | Nothing half-promoted reaches the base branch | gate.py; ci.yml |
| WF34 | A repository with a legacy `specs/` keeps it untouched as history; new changes go to `changes/`. When spec-kit is kept (`repo.md` "Spec-kit": `kept`), `spec.md` cites PRD rule IDs and defines no FR of its own, and `tasks.md` is not used: the prd-flow plan is | Two homes for the same behavior drift apart | repo.md; install.md |

## Flow rules added with prd-flow (survey, interview record, guards)

| ID | Rule | Why | Lands in |
|---|---|---|---|
| WF35 | The skill is named `prd-flow` (formerly `prd-gate`); `scripts/gate.py` keeps its name, its checks live in sibling modules named after their responsibility, and state lives in `.claude/prd-flow/state/<slug>/` | The old name described one step of five; the review found the name hid the workflow | skill SKILL.md; `scripts/gate.py`; IN14 |
| WF36 | C0 only when `docs/prd/INDEX.md` does not exist. In a repository with PRDs, a new product, a new module or an incoming spec document is a C5 of size L (new PRD variant): the surveyor sweeps the document against every existing PRD and every rule still passes confrontation and interview | A document dropped next to live PRDs contradicted them without anyone checking | SKILL.md "Cases"; classification.md |
| WF37 | Rules that come only from documents (not proven by code) are written `*(proposed)*` with Source `planned`; a proposed rule is C5 input, never C2: prd-flow confronts and interviews it, then replaces the marker with the approved one. `gate.py --final` fails on a proposed rule (G30) | A rule lifted from a document and never confirmed by a person was read as approved behavior | prd-writing.md; repo.md `proposed_marker`; PC13 |
| WF38 | Impact sweep K11 (semantic): read the Section column of every PRD file in `docs/prd/INDEX.md`, pick up to 8 sections whose subject could interact, read their rule tables, and list each rule the proposal would contradict, constrain or duplicate. The confrontation always carries `Checked:` and `Conflicts:` | A conflict phrased in other words in another section escaped the grep sweep | impact.md K11 |
| WF39 | Impact sweep K12 (history): each in-scope ID is searched in `docs/prd/CHANGELOG.md`; the confrontation shows what was decided, why, and which alternative was rejected | A rule was reversed without knowing it had been decided on purpose | impact.md K12 |
| WF40 | Impact sweep K13 (owner and shared PRD): when the change touches a section with a rule owner, the confrontation names the owner; when the PRD folder is shared with a sibling repository, it names the path that must receive the same change | Owners and sibling repositories were discovered after the PRD was written | impact.md K13; repo.md "Rule owners", "Shared PRDs" |
| WF41 | The sweep for parallel work also looks at remote branches (the in-scope IDs, the next free IDs and the change number); `gate.py --rules` and `--change` warn G27 on a collision | Two branches can take the same next ID or change number | impact.md K06; `gate_remote.py` |
| WF42 | The pre-interview marks each dimension `doc` (the PRD states it and the change does not touch it), `assumed` (a proposed default with its source), `open` (a question with a recommended default) or `n/a` (with a reason); a dimension the change touches is never `doc`. The confrontation shows the assumed ones in one block of at most 6 lines for the person to confirm or correct | Inferred defaults could enter the PRD without the person seeing them | workers.md surveyor; SKILL.md step 3 |
| WF43 | The interview record `interview.md` has one row per dimension with its state (`user`, `doc`, `assumed-confirmed`, `n/a`, `question`) and a `Confirmed:` line; `gate.py --rules` fails Q3 when a dimension is open, a `question` has no `Q-` row, or the confirmation is missing | WF16 was a promise made by the conversation; now the gate checks it | interview.md; `gate_interview.py` |
| WF44 | `gate.py --rules <file> --applied` fails Q4 when an approved row is not in the PRD with identical cells; the writer fixes the PRD, not the approved file, and step 6 shows the result | The writer retyped rows and the PRD drifted from what the person approved | prd-writing.md; workers.md `writer-prd`; `gate_prd.py` |
| WF45 | The C5 route has ten steps: state, surveyor, confrontation, interview with `decisions.md`, `writer-prd`, the person confirms the rule diff plus a summary of the non-table changes, `writer-trd`, planner, plan approval, execution. The TRD is never written before the PRD is confirmed | A TRD written before the person confirmed the rule is rework when the rule is adjusted | SKILL.md "C5 route" |
| WF46 | R09 (text in prd-flow SKILL.md): a behavior not covered by the approved rules enters the short C5 before code; a rule gap is never resolved by a task | Executors filled rule gaps with code and the decision never reached the PRD | SKILL.md R09; execution.md E05, E08 to E10; review.md V06 |
| WF47 | `changes/NNN-<slug>/decisions.md` records, per trade-off decided and per interview answer that chose between real options, the question, the decision, the rejected alternative and why (`DEC-NN`); it is committed with the PRD, and Promote copies the rows into the CHANGELOG entry | The why of a decision vanished with the session, and the next change reopened it | `docs/templates/change-decisions.md`; SKILL.md step 4; agent-plan.md |
| WF48 | `repo.md` "Rule owners" maps PRD files to the person who approves their rules. When the approver is not the owner, the interview does not close until the person states the owner agreed, and the CHANGELOG entry reads `decided by <owner>, written by <approver>`; `.github/CODEOWNERS` owns `docs/prd/**` by the same table | A rule in someone else's area was decided without them | repo.md; `.github/CODEOWNERS`; impact.md K13; IN15 |
| WF49 | A commit that touches the source folders carries a `Rules: <IDs>` trailer or `Case: none (<reason>)`; `scripts/gates.sh trailers [range]` checks it and CI runs it on pull requests; the executor's proposed message includes it | Code could not be traced back to the rule it implements | `scripts/commit_trailers.py`; `scripts/gates.sh`; ci.yml; execution.md E05 |
| WF50 | A C1 answer says, per rule cited, "verified in code" (one search found the Source symbol with a caller outside the tests) or "not verified" | Answers repeated the PRD as if it were the code | SKILL.md "Cases" C1 |
| WF51 | The surveyor runs on the strongest model for size L and on the default for M | The confrontation is the step whose miss costs the most | SKILL.md worker line |
| WF52 | The ceilings of agents (executor and fixer, reviewer) have one home, review.md V08; every other file cites V08 instead of restating numbers | Numbers restated in several files can disagree | review.md V08 |
