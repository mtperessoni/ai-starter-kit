# Creating the docs (PC) and installing the kit (IN)

## Creating the PRD and the TRD (PC)

| ID | Rule | Why | Lands in |
|---|---|---|---|
| PC01 | The first PRD documents what the code does today, defects included; a behavior that looks wrong is written as it is, with a "checked in code" callout and an open question. Fixing it is a later rule change | The source repository's PRD was written this way, read from the code at a pinned commit, and that is what made it trustworthy as a source of truth | prd-create P01 |
| PC02 | A repository can hold several PRDs, one folder each, when flows run independently (different actors, triggers or consumers). The source repository has two: the analysis run and the guided conversation | One PRD per independent flow keeps each section small and each reader focused | prd-create `anatomy.md` "How many PRDs" |
| PC03 | Every PRD has the same anatomy: summary, glossary with code names, scope, end-to-end journey with a diagram, one section per journey step, states and failures, audit and privacy, configuration, tenant matrix, problems of the current structure, spec versus code, risks, open questions | Readers and agents find the same thing in the same place in every PRD | prd-create `anatomy.md` |
| PC04 | Each step section explains before it rules: what it is, how it works, one concrete example, then the outcome table and the rule table | A rule table without the explanation is unreadable to product people | prd-create P04 |
| PC05 | The outline (PRDs, sections, prefixes, sources) is approved by the user before any section is written | Restructuring a written PRD costs more than approving an outline | prd-create P07 |
| PC06 | Facts come from mapper workers that read the code by area and write inventories; writers turn inventories into sections; the orchestrator never reads the code itself | Same economy as prd-flow: the long context stays in the workers | prd-create workers |
| PC07 | The PRD was split into one file per section after the source repository's agents read two files of 64k and 165k characters whole for every rule they needed; line numbers in Source went stale within hours and were dropped in favor of the TRD | Lazy loading and stable maps | prd-create P03; DS07 |
| PC08 | The TRD is created after the PRD, one file per feature, names only, every entry point verified to have a caller outside the tests, and each feature folder gets its `CLAUDE.md` map | The TRD routes a rule to its code; unverified maps mislead | trd-create T01 to T05 |
| PC09 | A codebase not organized by area gets the readiness plan (PC11) in its current layout; the move to feature folders (restructure: structure-only refactor, code moved by script, ratchet lowered per wave) is offered as an option with its cost, never required | The source repository went from one rule spread over 10 folders to one folder per PRD area; that move is costly, so it must not block the cheaper techniques | trd-create `restructure.md` |
| PC10 | Greenfield projects write the PRD by interview first (problem, actors, goals, non-goals, journey, variants, constraints), every Source `planned`; prd-flow C2 fills the Sources as code lands | The PRD exists before the code, so the code is planned against it | prd-create `greenfield.md` |
| PC11 | AI readiness of an existing repository is an incremental plan in its current layout (`trd-create` `reference/readiness.md`): maps, noise exclusion, characterization tests, splits of hotspot files and big tests, names, IDs, in waves ranked by `scripts/hotspots.py`. The move to feature folders is a separate option | A plan that starts with a restructure delays every benefit until the end; maps and noise exclusion pay on the first task | trd-create |
| PC12 | Hotspots rank the work: commits touching a file in a window times its lines; a large file nobody changes waits | Effort goes where agents actually read and edit; a large file nobody touches costs nothing until someone does | `scripts/hotspots.py` |
| PC13 | Rules that come only from documents (prd-create modes M3 and M4) are written `*(proposed)*` with Source `planned`; only rules proven by code are written as current behavior, and greenfield rules from the interview are approved | A document is a claim, not a decision (WF37) | prd-create SKILL.md and `reference/prd-writing.md`; `gate.py --final` G30 |
| PC14 | prd-create writes the `Example` column (DS32) for every rule with a number, a branch or a failure path, from the code or the interview answer | The worked case is what a test is written from | prd-create `reference/prd-writing.md`; `docs/templates/prd-section.md` |

## Installing and updating the kit (IN)

| ID | Rule | Why | Lands in |
|---|---|---|---|
| IN01 | The kit is one git repository; `install.sh` or `install.ps1` puts the `/ai-kit` skill and the global block on a machine; `/ai-kit install` adapts the kit to each project | One source, adapted per project; improvements flow back to every project | `install.sh`, `install.ps1`, `installer/ai-kit/` |
| IN02 | The skills are copied into each project and committed, so the whole team gets them with the repository, as in the source repository | A skill outside the repository is invisible to teammates | `ownership.md` |
| IN03 | Install detects the stack from manifests and from the project's own scripts; the project's scripts win over the recipe | Teams already know their commands | `install.md` I1 to I4 |
| IN04 | Every command is run once before it is written into `ai-kit.json`; a failing command becomes a question | A wrong command breaks every agent that calls it | `/ai-kit` K05 |
| IN05 | Install never overwrites an existing file: kit-owned files are replaced after a diff, project-owned files are merged | Projects adopt the kit without losing their rules | `ownership.md` |
| IN06 | The linter enforces function size, inheritance, shared state and import direction at the kit's limits with a baseline of today's violations, so CI is green on day one and the baseline only shrinks | Adoption without a big-bang refactor | stack recipes; AR17 |
| IN07 | A manifest records the kit version and the hash of each installed file; update replaces kit-owned files the project did not edit and proposes the rest as diffs | Updates are safe and reviewable | `.ai-kit/manifest.json`; `update.md` |
| IN08 | Install and update work on a branch, show the plan and wait for an explicit yes, commit once, never push | The project owner decides what lands | `/ai-kit` K02, K03, K06 |
| IN09 | Kit improvements found in a project go back to the kit repository first (MAINTAINING.md), then reach every project through `/ai-kit update` | One source of truth for the rules themselves | MAINTAINING.md |
| IN10 | Each CHANGELOG entry may carry an `On update:` line; `/ai-kit update` executes the lines of the entries between the project's version and the kit's | Changes that are not file copies (new folders, new config keys, seeded allowlists) reach existing projects | CHANGELOG.md; update.md |
| IN11 | Install describes how code is really organized in one free-text line (`layout`), whatever the structure is, declares `areas` and `map_dirs`, asks where a new area goes, and writes `.ignore` and `.claude/settings.json` (allow the gates, deny generated and vendored reads) | A guessed layout makes the checks fail or pass for the wrong files; the seeds make the noise exclusion (CE22) real from day one | install I3, I5, I8 |
| IN12 | `scripts/gates.sh setup` makes a fresh clone or worktree ready to test with one command (`commands.setup`), verified at install | Parallel agents work in fresh worktrees; each setup step guessed by an agent is a failed run and a retry | install I4 |
| IN13 | Doctor reports readiness per area against `docs/ai-readiness.md`: map present and short, TRD present, files and tests over limits, crowded folders, missing IDs, generated without marker, related-run time, top hotspots | Readiness drifts silently as code changes; one report per area shows where to spend the next task | doctor |
| IN14 | `/ai-kit update` on a repository with `.claude/skills/prd-gate/` shows the list, moves the project-owned `repo.md` into `.claude/skills/prd-flow/`, deletes the old skill folder, moves `.claude/prd-gate/state/` to `.claude/prd-flow/state/`, and replaces the old name in the project files the kit manages, each as a shown diff, asking before it overwrites a project-owned file. Each CHANGELOG `On update:` line is idempotent | Renaming the skill must not orphan the project's adapter or its in-flight state | `installer/ai-kit/reference/update.md`; CHANGELOG |
| IN15 | Install fills `.github/CODEOWNERS` from the "Rule owners" of `repo.md` (commented when there is none) and proposes contract snapshots (DS30, DS40) when `repo.md` lists a sibling consumer | Owners and contract guards are cheapest to set at install | `installer/ai-kit/reference/install.md`; `kit/.github/CODEOWNERS` |
| IN16 | Update migrates a hand-made `prd.html` to the generated one (`html_mode: generated`) only after showing the person a rendered preview; until then `html_mode` stays `hand` and the old checks apply | The person decides whether the generated page replaces the one they know | `installer/ai-kit/reference/update.md`; repo.md `html_mode` |
