# Code structure for AI (AR) and code constraints (CX)

An agent finds code by name (Glob, Grep) and pays for every file and every hop it reads. Small files, one responsibility, a name that says what the file does and the PRD ID at the top let the agent read only what the task needs. In the source repository, one product rule was once spread over 10 folders and one function had 4,120 lines.

## Structure rules (AR)

The feature-folder layout is recommended; every rule here holds in any folder structure (layers, legacy code, modules, mixes or anything else) and any language (AR20). The target repo's copy lives in `docs/code-structure.md` ([kit copy](../kit/docs/code-structure.md)). "Ratchet" means `scripts/ratchet.py` or the stack's linter enforces it; "review" means the reviewer and the planner check it.

| ID | Rule | Checked by | Why |
|---|---|---|---|
| AR01 | New code lives in the area of the PRD it implements. Recommended layout: one feature folder per PRD area (`<feature_root>/<f>/`), shared code used by three or more areas and not product rule in `infra/` (or `shared kernel` equivalent). A repository with another structure (whatever it is: layers, legacy modules, framework convention, a mix) describes it in its own words and declares it in `ai-kit.json` (`layout`, `areas`, `map_dirs`) and in `docs/code-structure.md` "This repository's layout"; code of an existing area stays in that area's files, a new area goes where that table says (default: a new feature folder) | review | PRD area, TRD file, code folder and tests line up 1:1 where the layout allows; a declared layout keeps the area-to-files mapping explicit where it does not |
| AR02 | One responsibility per file; the file name states it and is unique in the repository. Forbidden names: `helpers`, `utils`, `shared`, `common`, `misc`, `state`. `unique_name_exempt` holds the file names the framework imposes (from the recipe) | ratchet | A generic name cannot be found by Grep and attracts unrelated code |
| AR03 | Size limits: module up to 500 lines, function up to 80, class up to 300, test file up to 1,200. The recipe may adjust a limit for a verbose language, with the reason recorded in `docs/code-structure.md` | ratchet (modules, tests), linter (functions, classes) | Each read is bounded; an agent never needs a whole giant file |
| AR04 | Composition over mixins: a class receives small collaborators in its constructor, each readable alone. Never inherit from two in-repo classes. Inheritance or mixins the framework requires are allowed; the recipe lists them | linter | Behavior is traceable without walking a hierarchy |
| AR05 | Explicit state: no `nonlocal` or closures sharing mutable state; a session's state is an object passed along. The framework's own state primitive (hooks, refs, stores, actors) counts as explicit state | linter | Hidden state is invisible to Grep and to the reader |
| AR06 | Every module of an area cites the PRD IDs it implements in the first comment of the file, within `limits.id_header_lines` (the recipe raises it for languages whose files open with package and imports); every test cites the ID it proves. Checked for files of an area (feature folders and `areas`) | ratchet | One Grep by ID finds rule, code and test |
| AR07 | Every map folder (feature folders plus `map_dirs`) has a `CLAUDE.md` of at most 20 lines: a feature folder gets the feature map (`feature-CLAUDE.md`: responsibility, PRD IDs with their file, entry point, pieces, what must not break, where the tests are, link to its TRD); a folder holding several areas gets one row per area with its files there, PRD IDs and TRD link (`folder-CLAUDE.md`). Changing a piece changes the map in the same commit. One per map folder, not per folder | ratchet | Claude Code loads a subfolder's `CLAUDE.md` lazily, when a file of that folder is read, written or edited (not on Grep or Glob), and reloads it after `/compact`. Once loaded it is resent every call, so it must be short and only where the agent works: a product unit's folder, or a folder that holds several areas |
| AR08 | Re-exports only in a feature's public entry (the package or module index); importers use the defining module. The public entry has no side effects (no route mounting, no engine import) | review | Patches and Grep land on the real definition; side effects in the entry closed an import cycle |
| AR09 | Dependency directions are declared for this repository in `docs/code-structure.md` 'This repository's layout'. Examples: with feature folders, a feature uses `infra` and another feature only through its public entry, core features do not import peripheral ones, `infra` never imports a feature; with layers, upper layers use lower ones and never the reverse (for example entry, then services, then persistence); with modules, modules depend only through their public entry; any other structure declares its own directions there; no cycles in any structure (AR20) | linter | Changes stay local; cycles impossible |
| AR10 | Tests live where the stack expects them: beside the code (`<area folder>/tests/`) when the stack allows, otherwise the stack's mirrored tree with the same relative path. A test file is named after the module it proves with one of `tests.mirror_patterns`, so related tests find it. Harnesses have their own name; a test class imported by another file gets an alias starting with `_` where the collector would run it twice | review | Locality and a findable mirror name; the collector does not run imported classes twice |
| AR11 | Where the language patches by module path, mocks target the module of the caller, not the definer nor a re-export; with dependency injection, the fake is injected and this rule does not apply | review | A misplaced patch silently stops working |
| AR12 | Moving code is done by script (line ranges or AST), never retyped; the model decides the map and fixes imports | review | Retyping is slow and introduces bugs |
| AR13 | The TRD is 1:1 with the areas: `docs/trd/<area>.md` maps the area's files wherever they live, and every map `CLAUDE.md` that covers the area links to it | review | One map per area, no overlap |
| AR14 | Paths computed from the module's own location (`Path(__file__).parents[N]`, `import.meta.url`) use the module's real depth; after moving, check them | review | Moves break these silently |
| AR20 | The feature-folder layout is a recommendation, never a precondition. Every other rule (size, one responsibility, names, IDs, maps, tests, enforcement) applies in any layout and language; moving to feature folders is optional and incremental (C6 per area) | review | A rule that required a restructure first would keep the existing repositories, the ones that need it most, from adopting any of them |
| AR21 | In a legacy area, a task that must change a file over the limits first extracts the responsibility it touches into a new module named after it (by script, AR12), then changes the new module; it never grows the file (the ratchet refuses it) | ratchet, review | The over-limit file is never read whole again for that change, and each task shrinks the debt instead of adding to it |
| AR22 | Greppable wiring: every call site names its target literally. No dispatch through names assembled at runtime (string-built function or method names, reflective lookup by computed name, imports by computed path); a dispatch table lists its targets by name. Wiring by framework convention is allowed when the area TRD "How it enters the flow" names the convention and the files it binds | review; linter rule where the recipe has one | A name built at runtime is invisible to Grep, so the agent reads whole files or concludes the code is unused |
| AR23 | At most `limits.files_per_dir` (20) code files directly in one folder, tests excluded; a crowded folder splits into subfolders by area or responsibility | ratchet (`crowded_dirs`) | A listing of a crowded folder costs tokens and hides which file matters; names stop being scannable |
| AR24 | Complexity: cyclomatic complexity up to 10, nesting depth up to 4, parameters up to 5 per function | linter with baseline (recipe); review | A function with many branches or arguments cannot be understood, or changed safely, from a ranged read |
| AR25 | Dead code is deleted, not kept: unused modules, functions and exports fail the stack's dead-code check with a shrink-only baseline; symbols reached only through framework reflection or DI go to that tool's allowlist | linter (recipe); review plus DS13 | An agent cannot tell dead code from live code and spends reads and edits on code nothing calls |
| AR26 | Duplicated blocks are detected with a shrink-only baseline; a fix inside a duplicated block fixes every copy or extracts the block | linter (recipe); review | A fix applied to one copy leaves the others with the defect, and Grep finds all of them only after the damage |
| AR27 | In a language with gradual or optional typing, type checking strictness only goes up, per module, with a shrink-only baseline; module boundaries and public functions are typed. Not applicable to statically typed languages | type checker (recipe) | Types let the agent check a change without running it and read a signature instead of the body |
| AR28 | Generated files match `generated_patterns`, start with a generated marker in their first lines (`generated` plus `do not edit`, or the generator's standard line), are excluded from the other structure checks, from search and from agent reads; a change regenerates them, never edits them | ratchet (`generated_without_marker`) | A hand edit to a generated file is overwritten at the next run, and its size floods search results and reads |

## The ratchet

| ID | Rule | Why |
|---|---|---|
| AR15 | A structural check fails when a "ratchet" rule is violated outside an allowlist | Rules nobody enforces rot |
| AR16 | The allowlist only shrinks: a value above its entry fails; an entry that is already within the limit, or whose target no longer exists, also fails until removed; an entry that dropped must be lowered | Progress is locked in automatically |
| AR17 | Start with an allowlist of the current state (`python scripts/ratchet.py --init`); no refactor is required before adopting the rules | Adoption on day one, improvement over time |
| AR18 | The ratchet is always run with the related tests of any task (TS02) | Violations are caught in the task that creates them |
| AR19 | Split of enforcement: `scripts/ratchet.py` checks what text can see in any stack (module and test file size, generic names, duplicate names, PRD ID in area module headers, map `CLAUDE.md` present and short, crowded folders (AR23), generated markers (AR28)), and validates the layout config: an area whose globs match no file, or a `map_dirs` entry that does not exist, fails and is never allowlisted. Function and class size, inheritance, closures, complexity, dead code, duplication, typing and import direction are syntax: the stack's linter enforces them, configured at setup with the same limits and its own baseline | The kit stays stack-free; the source repo did all of it in one AST test because it had one language |

## Code constraints (CX)

Recommended constraints for the target repo's `AGENTS.md` "Critical constraints". Adjust to the domain; each one prevented a real class of defect in the source repository.

| ID | Rule | Why |
|---|---|---|
| CX01 | Never swallow an exception and never fire-and-forget: every failure is persisted or logged with its cause; an empty `catch`/`except` is a violation | Silent failures were the hardest bugs to find |
| CX02 | Never hardcode a credential, token, key, model id, prompt or per-customer rule. It is typed configuration or versioned data | Hardcoded secrets leaked through exports |
| CX03 | Configuration is typed and validated at boot; the service refuses to start on missing or malformed config | A bad config found in production is an outage |
| CX04 | Never branch on a customer or tenant name (`if tenant == "X"`); per-tenant behavior is a configuration row resolved at runtime | Copy-pasted per-customer flows are the anti-pattern |
| CX05 | Framework and vendor types do not cross into the domain layer; framework at the edges, domain testable in isolation | Domain tests stay fast and offline |
| CX06 | Every side effect logs, structured, with the correlation ids of the request | Auditability |
| CX08 | An environment variable only for what changes per environment (secret, address, route, rollout flag); product behavior goes to typed configuration in code or versioned data | Behavior hidden in env vars cannot be reviewed, tested or rolled back per tenant |
| CX09 | `.env.example` lists every configuration key with a safe placeholder; a test asserts every settings field has a key there and no value has a secret shape. A removed variable is ignored, and a test proves it is no longer a setting | The example file is the contract with deploy; it drifted silently before the test |
| CX10 | Secrets scan in CI over tracked files (gitleaks with the default rules plus an allowlist of generated paths) | A credential in a commit is a leak even after revert |
| CX11 | Every text file is LF in the repository and every checkout (`.gitattributes`: `* text=auto eol=lf`), whatever the machine's `core.autocrlf` says | A CRLF checkout on Windows broke byte-for-byte comparisons and produced lint noise |
| CX07 | A behavior that the product decides by an AI agent is never replaced by a code heuristic on failure (term lists, similarity cuts, reserve plans); offer agent-based retries or explicit end states. A code check that is a safety guardrail is named as such | Heuristic fallbacks produced the very defects the agent was meant to fix (applies to AI-driven products) |
